When you ran:

```bat
net use \\mogdnfs1\IPC$ /user:ipg\jzoltak
```

and successfully entered the password, Windows established a valid SMB session to **MOGDNFS1** using the correct credentials.

## What likely happened

1. Joe's laptop did not have a valid authentication session to **MOGDNFS1**.
2. The existing **L:** drive mapping was trying to reconnect using outdated, invalid, or unavailable credentials.
3. As a result, Windows reported errors such as:
   - "The user name or password is incorrect"
   - "Cannot contact a domain controller"
4. By manually connecting to:

```text
\\mogdnfs1\IPC$
```

you forced Windows to create a new authenticated SMB session using:

```text
ipg\jzoltak
```

5. Windows can now reuse that authenticated session when accessing:

```text
\\mogdnfs1\InteplastBuild\Glendale\Local
```

## Next, try

```text
\\mogdnfs1\InteplastBuild\Glendale\Local
```

It may work immediately without prompting again because the SMB session is already established.

## Why did the P: drive work while the L: drive not?

Your `cmdkey /list` output showed cached credentials for:

```text
Target: MOMBNFS1
User: ipg\jzoltak
```

This suggests Windows already had valid credentials cached for **MOMBNFS1** (P: drive), but not for **MOGDNFS1** (L: drive).

Therefore:

- **P:** ✅ Authenticated automatically
- **L:** ❌ Could not authenticate until a new SMB session was established manually

## Conclusion

Based on the test results, the most likely root cause was a missing or stale authentication session to **MOGDNFS1**, rather than a VPN, DNS, network, or permissions issue.

If the **L:** drive maps successfully now, that would strongly confirm the diagnosis. 👍
